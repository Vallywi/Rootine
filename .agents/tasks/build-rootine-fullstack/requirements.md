# Rootine P0/MVP Requirements

## Summary

Rootine is a mobile-first, responsive web app for students that combines personal task management, a timestamp-based Pomodoro timer, visible plant growth, and a persistent personal Garden. This document defines only the complete P0/MVP. It is derived from `docs/product/PRD.md` version 0.4 and `docs/design/UX-UI-PLAN.md`; those documents remain authoritative if implementation details later conflict with this checklist.

The MVP includes a real frontend, backend, database, migrations, secure email/password account flows, task CRUD, per-account Pomodoro settings, focus and break sessions, completion notifications, and owner-only Garden records. All controls must work end to end. The project must contain no fake API data, placeholder-only screens, or nonfunctional buttons.

Requirement keywords such as **must**, **must not**, and **only** are binding for P0. Validation and acceptance work may be documented or performed manually because committed automated test files are outside this task.

### Assumptions and resolutions for unresolved or conflicting source material

The following choices make the MVP implementable without adding P1/P2 scope. They are proposed requirements for design review.

1. **Session closure, logout, and post-target return (PRD OQ-5):** Closing or backgrounding the browser does not give up a session. An active session continues against its stored target timestamp; a paused session remains paused. Before the target, reopening or logging back in restores it. At or after the target, the next server synchronization reconciles it as completed exactly once. Explicit confirmed Give up is the only P0 action that produces a withered focus result. Logging out while a focus or break is active or paused requires confirmation and plainly states that the timer state will be retained. No alert is promised while the browser is fully closed.
2. **Break behavior and counter reset (PRD A-3/OQ-6):** A break is offered but starts only after **Start break** is selected. An active break has no Pause, Resume, or early-end control because the approved UX plan does not define those controls. A long-break interval counter resets when the long break is offered, even if the user skips the offer. Skipping a short break does not reset the counter.
3. **Growth thresholds (PRD A-6/OQ-7):** Seed, Sprout, Small plant, and Full plant begin at 0%, 25%, 60%, and persisted 100% completion respectively.
4. **Withered history (PRD A-4/OQ-13):** Confirmed give-up results appear in a separate **History** filter in Garden and never in the default completed-plants collection.
5. **Task deletion (PRD OQ-17):** P0 uses the approved confirmation-dialog baseline, not timed Undo. The safer **Keep task** action receives initial focus. Historical sessions retain a copied task title after task deletion.
6. **Notification defaults and copy (PRD OQ-18):** Completion sound defaults to off. Browser notifications default to off and use the generic copy proposed in the UX plan: “Focus session complete. Return to Rootine when you’re ready.” or “Break complete. Rootine is ready.” No task or account detail appears in a notification.
7. **Task limits (PRD OQ-20):** A normalized task title is 1–200 Unicode characters after trimming leading and trailing whitespace. An optional estimate is a whole number from 1–999. The original entered title may retain internal spaces and line-safe Unicode; markup is always treated as text.
8. **Plant catalog and assets (PRD A-1/OQ-14):** P0 ships three selectable plant types. Each has original project-owned CSS/SVG visuals for Seed, Sprout, Small plant, Full plant, and Withered states. No externally licensed asset is required.
9. **Account rules and session lifetime (PRD OQ-16):** Passwords accept 12–128 characters, including spaces and Unicode, with no arbitrary composition rule; paste and password managers remain supported. An authenticated web session has a 12-hour idle lifetime and a 7-day absolute lifetime. A password-reset credential expires after 30 minutes and is single-use. These defaults may be tightened in design, but not weakened without product approval.
10. **Password-reset delivery:** Reset delivery uses a provider abstraction. Production requires a configured real email provider. Local development uses a clearly identified local-only outbox or mail-capture provider and truthfully reports that no external email was sent; reset credentials must not be written to normal application logs. No credentials are hard-coded.
11. **Data rights and retention (PRD OQ-10):** Account export and deletion controls are not included in P0 because retention and verification rules are unresolved. P0 must still minimize collected data and avoid making unsupported deletion or retention promises.
12. **Time zones and statistics (PRD OQ-9):** Statistics and streaks are P1, so their calendar-boundary decision does not block P0. Garden dates use the user’s browser-local presentation of an unambiguous stored timestamp.
13. **Technology choice (PRD OQ-2/OQ-16):** The requirements do not choose an implementation stack. The design phase must select one maintained, TypeScript-first stack and lock it before implementation, while retaining every security and run-local requirement below.

## Functional Requirements

### Project shape and end-to-end integration

- [ ] **FR-001:** The workspace contains an independently runnable frontend in `frontend/` and backend in `backend/`, connected through a typed and server-validated API contract. All frontend server access goes through one centralized API client. [Trace: task brief “Frontend…backend,” “typed/validated API contract”; PRD §13.4]
- [ ] **FR-002:** Persistent storage and ordered migrations cover users, authenticated web sessions, per-user settings, tasks, focus and break sessions, active/paused timing state, plant catalog records, Garden outcomes, password-reset credentials, and the minimal uniqueness/audit fields needed for ownership and idempotency. [Trace: task brief item 12; PRD §12.4, BR-1–BR-14]
- [ ] **FR-003:** Any seed/demo data contains no embedded user credentials and creates no authentication bypass. Catalog seed data may include only the three P0 plant definitions and other non-secret reference data. [Trace: task brief item 12; PRD §12.2]
- [ ] **FR-004:** The authenticated app provides Focus, Tasks, Garden, and Settings navigation only. The first authenticated destination is Today / Focus. Public routes provide Landing, Register, Log in, Request password reset, and Set new password. [Trace: PRD §7.1–§7.2; UX plan §2.1–§2.2]

### Accounts, authentication, and session restoration

- [ ] **FR-005:** A visitor can register with a syntactically valid email and a 12–128-character password. Email is required, trimmed, and normalized consistently for account matching. Password input permits paste and password managers. Successful registration creates default settings and enters an authenticated session. [Trace: PRD FR-1, AC-1, NFR-8; UX plan §3.1, §5.5]
- [ ] **FR-006:** Duplicate, invalid, and unexpected registration failures use a generic response that does not confirm whether an account exists and never exposes raw provider, database, or stack information. [Trace: PRD FR-1, NFR-10; UX plan §3.1, §9.1]
- [ ] **FR-007:** A registered user can log in and explicitly log out. Login credential errors are generic. Protected routes and APIs reject missing, expired, invalidated, or cross-user credentials. Reloading the app restores a still-valid authenticated session without storing a reusable authentication secret in browser script-accessible storage. [Trace: PRD FR-2, NFR-12–NFR-13, AC-1/AC-24; UX plan §3.1]
- [ ] **FR-008:** Logout invalidates the current server-side session. If a timer is active or paused, logout first presents an accessible confirmation explaining that the timer state will be retained under Resolution 1; cancel leaves both authentication and timer unchanged. [Trace: PRD §10 logout edge case, NFR-12, OQ-5; UX plan §5.4, §9.1]
- [ ] **FR-009:** Password-reset request accepts an email and always returns the same non-enumerating response. A valid reset credential can set a compliant new password once within 30 minutes. Modified, expired, or reused credentials fail without changing the password and offer a new request. Reset credentials are unpredictable and stored in a non-recoverable form. [Trace: PRD FR-3, NFR-18, AC-23; UX plan §3.1]
- [ ] **FR-010:** Reset-message delivery follows Resolution 10. A provider failure returns a safe retryable error to the request workflow without revealing account existence; it is logged only as a sanitized operational event, never with email content, password, or reset credential. [Trace: task brief item 1; PRD NFR-10/NFR-18; UX plan §9.3]

### Personal tasks

- [ ] **FR-011:** An authenticated user can list only their own active and completed tasks. Each task displays its wrapped title, explicit Active/Complete state, completed-focus count, estimate progress when present, and visible Focus this task, Edit, Mark complete/active, and Delete actions. [Trace: PRD FR-24/FR-26, BR-9; UX plan §3.3]
- [ ] **FR-012:** A user can create a task with a required normalized title of 1–200 characters and an optional estimate of 1–999 whole focus sessions. Blank, over-limit, fractional, zero, negative, wrong-type, and malformed values do not persist. [Trace: PRD FR-24, AC-15, OQ-20; UX plan §5.5]
- [ ] **FR-013:** A user can edit the allowed title and estimate fields of their own task. Invalid edits preserve the prior persisted task and retain other valid form input for correction. [Trace: PRD FR-24, AC-15; UX plan §3.3]
- [ ] **FR-014:** A user can mark their own task complete and later mark it active without deleting the task or its history. The UI announces the persisted state change and never reports success before the server confirms it. [Trace: PRD BR-13, FR-24; UX plan §4.1]
- [ ] **FR-015:** Deleting a task uses the confirmation in Resolution 5. Successful deletion removes it from the task list and future session selectors but does not delete historical sessions or their copied task title. A repeated delete request is harmless. [Trace: PRD BR-11, FR-24, AC-15/AC-16; UX plan §3.3, §5.4]
- [ ] **FR-016:** Any endpoint receiving a task identifier enforces authenticated ownership at the data boundary. A user cannot infer, read, select, update, complete, reopen, or delete another user’s task by changing a route, query, or request body identifier. [Trace: PRD BR-9, NFR-13, AC-12; UX plan §9.1]

### Pomodoro settings and focus setup

- [ ] **FR-017:** Every new account receives per-account defaults of 25-minute focus, 5-minute short break, 15-minute long break, and a long break after 4 completed focus sessions. Sound and browser notifications default to off; motion defaults to Use device setting. [Trace: PRD FR-11/FR-12/FR-36, AC-8/AC-17; UX plan §3.10]
- [ ] **FR-018:** With no active or paused focus or break, a user can save whole-number settings only within: focus 15–60 minutes, short break 5–15, long break 10–30, and interval 2–6. Invalid input preserves the last persisted values and the entered values for correction. Valid settings survive logout/login. [Trace: PRD FR-12, AC-17; UX plan §3.10, §5.5]
- [ ] **FR-019:** While any focus or break is active or paused, all four Pomodoro settings are visibly locked and server-side updates are rejected. A session snapshots its type, planned duration, applicable interval, plant, and optional task when created; later settings changes affect only future sessions. [Trace: PRD FR-12, BR-12, AC-17; UX plan §3.5, §3.10]
- [ ] **FR-020:** Focus setup offers the three complete plant types, the saved focus duration with an optional one-session whole-minute override from 15–60, and either **No task** or one owned, non-deleted task. A missing/invalid plant or duration blocks start and identifies the field; No task is always valid. [Trace: PRD FR-6, FR-25, AC-2/AC-16; UX plan §3.4]
- [ ] **FR-021:** Start focus prevents duplicate submission. The server atomically creates at most one unresolved active/paused focus-or-break timer for the account. If one already exists, the client restores it rather than creating another. [Trace: task brief item 4; PRD BR-1, AC-2/AC-18; UX plan §3.4]

### Timer, focus outcomes, and breaks

- [ ] **FR-022:** The active focus screen displays a textual Active state, timestamp-derived remaining time, planned duration, plant name and textual growth stage, optional selected task, and visible Pause and Give up controls. Paused state replaces Pause with Resume and clearly says Paused. [Trace: PRD FR-7–FR-9; UX plan §3.5]
- [ ] **FR-023:** Timer truth comes from persisted timestamps and paused remaining time, not accumulated client interval ticks. Refresh, browser backgrounding, clock-display ticks, and multiple tabs cannot reset or extend the planned duration. [Trace: PRD FR-8, NFR-2, AC-3/AC-4; UX plan §3.5]
- [ ] **FR-024:** Pause freezes the authoritative remaining duration and plant progress. Resume creates a new target from that frozen duration. Repeated, stale, or concurrent Pause/Resume requests are idempotent or rejected as invalid transitions without changing elapsed progress. [Trace: PRD FR-9, AC-18, BR-6; UX plan §4.4]
- [ ] **FR-025:** Give up is available from active and paused focus states and always opens an accessible confirmation. Cancel/Escape restores the unchanged state. Confirm atomically records exactly one given-up outcome, immediately ends the timer, creates one gentle withered History result, gives no plant/task/completion credit, and can never later become completed. [Trace: PRD FR-10/FR-17, BR-2/BR-3, AC-7; UX plan §3.6, §5.4]
- [ ] **FR-026:** Focus progress exposes Seed from 0%, Sprout from 25%, Small plant from 60%, and Full plant only after 100% completion is persisted. Every state has text as well as original CSS/SVG art. Stage changes use restrained motion or immediate static swaps when reduced motion applies. [Trace: PRD FR-14/FR-15, A-6, AC-5; UX plan §7.6–§7.7]
- [ ] **FR-027:** Reaching zero causes a server-authoritative, idempotent completion. One completed focus produces exactly one completed session outcome, one persistent mature Garden plant, and at most one completed-session increment for its snapshotted task. It cannot also become given up. Retries, refreshes, stale requests, or concurrent tabs grant nothing twice. [Trace: PRD FR-16, BR-2/BR-6/BR-11, AC-6; UX plan §4.4]
- [ ] **FR-028:** A completed focus offers the correct short or long break. Breaks start only after **Start break**. The interval advances only for completed focuses and follows Resolution 2. A skipped offer creates no break session and grants nothing. [Trace: PRD FR-11, BR-4/BR-5, AC-8; UX plan §3.7]
- [ ] **FR-029:** An active break uses a timestamp-based countdown, displays Short break or Long break and its remaining time, and shows no plant growth. At zero it records one break completion. Breaks never create Garden plants, withered results, task credit, focus totals, or rewards. [Trace: PRD BR-4, FR-13, AC-8; UX plan §3.7]
- [ ] **FR-030:** Refresh or relaunch restores the same active or paused focus/break with its state, task snapshot, plant, stage, and correct time. If its target has passed, the server reconciles the result under Resolution 1 before another session can start. A recoverable persistence failure exposes retry/reconciliation and never shows an unpersisted reward as saved. [Trace: PRD J-4, NFR-7/NFR-11, AC-4; UX plan §3.5–§3.7]

### Garden, alerts, and notifications

- [ ] **FR-031:** Garden’s default view lists only the authenticated user’s completed plants. Each card includes plant type, full-plant visual, completion date, and planned focus duration. A separate History filter lists that user’s withered outcomes with explicit Ended text. [Trace: PRD FR-19, A-4, AC-9; UX plan §3.8]
- [ ] **FR-032:** Garden supports first-plant empty, empty History, loading, load-error with Try again, stale/offline, and generic access-denied states. It must not expose the existence or details of another user’s Garden/session record. [Trace: PRD §7.2, NFR-13; UX plan §3.8, §12]
- [ ] **FR-033:** Every persisted focus completion and break completion produces one always-available in-app completion alert. Each may independently play one sound only when sound is enabled. Sound failure never changes or blocks the saved outcome. [Trace: PRD FR-13, BR-14, AC-19; UX plan §10]
- [ ] **FR-034:** Browser notification permission is requested only in direct response to **Enable Notifications**, never on load, registration, login, or session start. Settings reflects not requested/off, granted with an app preference, denied/revoked with browser-settings guidance, or unsupported. Denied/revoked/unsupported states retain in-app alerts and do not repeatedly prompt. [Trace: PRD FR-35/FR-36, AC-20; UX plan §3.10, §10]
- [ ] **FR-035:** A granted and app-enabled browser notification produces at most one generic notification per persisted focus or break completion, independent of sound. It contains no task title, email, identifier, token, or other private content. Settings states that delivery is not reliable while Rootine is fully closed. No push/PWA/backend delivery is included. [Trace: PRD FR-36, BR-14, NFR-20; UX plan §10]
- [ ] **FR-036:** Completion feedback is deduplicated by persisted event identity across retries and tabs so one event cannot produce duplicate in-app alerts, sounds, browser notifications, plants, task credits, or conflicting result states. [Trace: PRD BR-6/BR-14, NFR-11/NFR-20; UX plan §5.3]

### Required interface states and content

- [ ] **FR-037:** Landing, authentication, Focus, Tasks, Garden, and Settings implement their documented empty, loading, saving, success, validation, error, offline, session-expired, and permission states with a specific next action. Decorative content never hides the primary action. [Trace: PRD §7.2, §10; UX plan §3, §12]
- [ ] **FR-038:** Network loss or a failed write never reports a task change, settings change, session result, Garden plant, deletion, or task credit as saved. Locally derivable timer display may continue with a visible offline state, followed by server reconciliation or explicit retry. Full offline operation is not required. [Trace: PRD §10 network edge case, NFR-7/NFR-10; UX plan §3.5, §9.3]
- [ ] **FR-039:** User-controlled text is rendered as text, including markup- and script-like task titles. If plant art fails, the timer and controls remain usable and the plant name and stage remain visible. [Trace: PRD §10 asset/XSS edge cases, NFR-14; UX plan §3.5]

## Non-Functional Requirements

### Security, privacy, and data integrity

- [ ] **NFR-001:** Passwords use a current established salted adaptive password hash. Plain-text passwords, reset credentials, and authentication tokens never enter source code, persistent logs, analytics, or user-facing errors. [Trace: PRD NFR-8, §12.2, AC-23]
- [ ] **NFR-002:** Authentication uses server-managed sessions with cookies marked `HttpOnly`, `Secure`, and an appropriate `SameSite` value in deployed environments. Session identifiers rotate when authentication state changes, expire after the documented idle/absolute lifetimes, and are invalidated on logout. Local and production transport/cookie behavior is documented; local development must not disable validation, authorization, CSRF, rate limits, or secure error handling. [Trace: task brief item 11; PRD NFR-12, AC-24]
- [ ] **NFR-003:** Every state-changing cookie-authenticated request requires a valid CSRF defense. Missing, invalid, or cross-session proof causes rejection with no state change. CORS permits only explicitly configured frontend origins, required methods/headers, and credential use; wildcard credentialed origins are forbidden. [Trace: task brief item 11; PRD NFR-15, AC-25]
- [ ] **NFR-004:** The backend validates every external input for required/optional status, primitive type, format, length, numeric range, identifier shape, and allowed state transition before persistence. Database access uses a parameterized ORM/query API. Output encoding prevents stored and reflected script execution. [Trace: task brief item 11; PRD NFR-14, AC-25]
- [ ] **NFR-005:** Ownership is enforced in backend data access for settings, tasks, sessions, break records, Garden/history outcomes, and any account record. Client-provided user or record identifiers never establish ownership. Unauthorized and not-found responses do not disclose whether another user’s record exists. [Trace: PRD BR-9, NFR-13, AC-12]
- [ ] **NFR-006:** Persisted uniqueness and transactional state transitions enforce one unresolved timer and one final outcome/plant/task credit per focus session. The server, not client UI state, owns these invariants. [Trace: PRD BR-1/BR-6, NFR-11]
- [ ] **NFR-007:** Authentication/reset abuse controls are enabled in local and deployed modes. Within a rolling 15-minute window, login permits no more than 10 failed attempts for the combined account/client signal and registration no more than 5 attempts per client signal; reset request permits no more than 5 attempts per account/client signal per hour. Exceeding a limit returns a generic `429` response without account enumeration. [Trace: PRD NFR-17, AC-26]
- [ ] **NFR-008:** Responses use production-safe errors and sanitised structured logging. User-facing and logged errors exclude passwords, reset credentials, auth/CSRF tokens, sensitive task text, raw query details, and user-facing stack traces. Security-relevant failures record only the minimal event type, time, safe actor/session reference, result, and correlation reference needed for review. [Trace: PRD NFR-10, §12.2; UX plan §9.3]
- [ ] **NFR-009:** The backend emits appropriate security headers, including a restrictive Content Security Policy, clickjacking protection through CSP `frame-ancestors`, MIME sniffing protection, a suitable referrer policy, and permissions policy. Deployed authenticated traffic uses HTTPS, redirects HTTP to HTTPS, and loads no active mixed content. [Trace: task brief item 11; PRD NFR-16, AC-26]
- [ ] **NFR-010:** Secrets exist only in ignored environment files or a deployment secret store. Client bundles contain no private secrets. Data collection is limited to fields mapped to users, settings, tasks, sessions, Garden/history, resets, and security/idempotency needs; there is no advertising, undisclosed analytics, tab surveillance, keystroke collection, precise location, or unrelated browsing data. [Trace: PRD NFR-9/NFR-19, §12.1, AC-27]
- [ ] **NFR-011:** Before release, the project records a lightweight threat model for account takeover, credential/reset abuse, session theft, broken object ownership, XSS, CSRF, request replay/duplicate outcomes, secret exposure, and notification privacy. A dependency/security scan has no unresolved critical finding; each high finding is fixed or documented with owner and mitigation. [Trace: PRD §12.2, NFR-19, AC-27]

### Accessibility and inclusive interaction

- [ ] **NFR-012:** All P0 screens target WCAG 2.2 AA and use semantic landmarks, headings, lists, forms, buttons, labels, dialogs, and status regions. Every input has a persistent label and programmatically associated instructions/errors. [Trace: PRD NFR-5, §12.3; UX plan §8]
- [ ] **NFR-013:** All actions work by keyboard in a logical order with a visible focus indicator. Dialogs trap focus, begin on the safer action, close with Escape as cancel, and restore focus to the invoker. No required action is hover-only, gesture-only, sound-only, motion-only, artwork-only, or color-only. [Trace: PRD AC-10; UX plan §5.4, §8]
- [ ] **NFR-014:** The timer is discoverable on demand but is not announced every second. Assistive technology receives restrained announcements for start, pause with remaining time, resume, stage changes, completion, break transitions, errors, and persisted task/settings results. [Trace: PRD §12.3; UX plan §8]
- [ ] **NFR-015:** Normal text has at least 4.5:1 contrast, large text and meaningful non-text indicators at least 3:1, and focus indicators at least 3:1 against adjacent colors in every final default, hover, focus, active, selected, disabled, error, and overlay state. [Trace: PRD NFR-5; UX plan §7.2]
- [ ] **NFR-016:** Rootine respects `prefers-reduced-motion` and the in-app Use device setting/Reduce motion preference. Reduced motion replaces nonessential 150–250 ms growth transitions with static changes without losing content. No content flashes more than three times per second. [Trace: PRD NFR-6; UX plan §7.7, §8]

### Responsive, visual, compatibility, and performance requirements

- [ ] **NFR-017:** The UI is mobile-first and reflows from 320 CSS px through desktop without horizontal page scrolling. Phone uses labeled bottom navigation with safe-area padding; wide desktop uses equivalent labeled side navigation and a readable centered content width. Portrait and landscape expose the same actions. [Trace: PRD NFR-3/NFR-21, AC-21; UX plan §2.2, §6]
- [ ] **NFR-018:** Every P0 interactive target is at least 44×44 CSS px. Primary phone controls remain thumb-reachable. At 200% zoom and with a mobile keyboard or safe-area inset, the focused field, its error, navigation, and primary timer/task actions remain reachable without two-dimensional scrolling. Browser/pinch zoom is not disabled. [Trace: PRD NFR-5/NFR-21, AC-22; UX plan §6, §8]
- [ ] **NFR-019:** The approved visual direction uses warm cream `#F7F3E8` backgrounds, white surfaces, forest green `#2F5D50` primary actions, deep charcoal green `#1F2D27` text, rounded 8/12/16 px controls/cards/dialogs, restrained borders/shadows, and limited leaf, earth, amber, and terracotta accents according to the UX plan’s contrast restrictions. The result is cute, cozy, botanical, calm, and polished without childish decoration, clutter, constant animation, or unlicensed assets. [Trace: task brief item 8; UX plan §7]
- [ ] **NFR-020:** Core screens become usable within 3 seconds on a recorded team test device/network profile. A 25-minute focus timer remains within 1 second of wall-clock time, including at least 5 minutes in a background tab. [Trace: PRD NFR-1/NFR-2, AC-3]
- [ ] **NFR-021:** Complete P0 flows support current stable Chrome, Edge, Firefox, and Safari available to the team. Any unavailable Safari platform is documented. Browser-notification API absence activates the documented fallback rather than failing the core flow. [Trace: PRD NFR-4, AC-13]

- [ ] **NFR-024:** Package scripts provide development, production build, start/serve, type-check, lint, migration, and dependency/security-review commands appropriate to the selected stack. ## Acceptance Criteria

### Core behavior

1. **AC-001 — Clean setup:** On a clean local environment with only documented prerequisites, following `README.md`, copying both `.env.example` files, configuring non-secret local values, running migrations, and starting the documented commands produces a working frontend/backend/database without embedded credentials.
2. **AC-002 — Registration and authentication:** A valid new user registers and reaches Today / Focus with 25/5/15/4 defaults, then logs out and back in. Invalid and duplicate registration and invalid login show generic messages that do not reveal whether the email exists. [Covers PRD AC-1]
3. **AC-003 — Session restoration and invalidation:** Refresh restores a valid login. After logout, the previous cookie cannot call any protected endpoint. A session idle beyond 12 hours or older than 7 days is rejected and the UI directs the user to log in. Cookie inspection in a deployed HTTPS environment shows `Secure`, `HttpOnly`, and the approved `SameSite` value. [Covers PRD AC-24]
4. **AC-004 — Password reset:** Reset requests for existing and unknown emails show the same response. In the documented local outbox, one valid reset credential changes the password once within 30 minutes; reuse, modification, or expiry fails. No reset credential appears in application logs. [Covers PRD AC-23]
5. **AC-005 — Task lifecycle:** An owner creates a task with title and optional estimate, edits it, marks it complete, reopens it, and deletes it through the confirmation dialog. The list and focus selector reflect each persisted state, while old linked sessions retain the copied title. [Covers PRD AC-15/AC-16]
6. **AC-006 — Task validation:** Titles that are blank, whitespace-only, or over 200 characters and estimates that are non-numeric, fractional, below 1, or above 999 are rejected on client and server. A 200-character title and estimates 1 and 999 persist. Valid input in other fields remains after an error.
7. **AC-007 — Settings:** New defaults are 25/5/15/4. Boundary values 15/5/10/2 and 60/15/30/6 save and survive logout/login; fractional and out-of-range values do not replace saved settings. During any unresolved timer, client controls are locked and a direct API update is rejected without changing settings or the timer snapshot. [Covers PRD AC-8/AC-17]
8. **AC-008 — Focus setup:** Each of the three selectable plants has Seed, Sprout, Small plant, Full plant, and Withered visuals. Starting with no task and starting with one owned, non-deleted task both work with a 15–60 whole-minute duration; invalid plant/task/duration input does not create a session. [Covers PRD AC-2/AC-16]
9. **AC-009 — One timer invariant:** Rapid repeated Start requests and concurrent Start requests from two tabs produce one unresolved timer. The second client restores the existing timer. A break and focus cannot be active simultaneously. [Covers PRD BR-1]
10. **AC-010 — Timer accuracy:** During a 25-minute run containing at least 5 backgrounded minutes, displayed remaining time differs from wall-clock elapsed time by no more than 1 second at the measurement points. Returning from background recomputes from authoritative timestamps. [Covers PRD AC-3]
11. **AC-011 — Pause and resume:** Pause freezes remaining time and stage. Refresh while paused restores both. Resume continues from the frozen remainder without resetting planned duration. Repeated or cross-tab Pause/Resume requests apply each valid transition once. [Covers PRD AC-18]
12. **AC-012 — Refresh, closure, and logout:** Refresh or reopen before target restores the same active focus, or restores a paused focus without reducing its frozen remainder; both retain the task, plant, and stage. Confirmed logout invalidates authentication but retains timer state. Logging in before an active focus target restores it, while logging in after that target reconciles one completion; a paused focus remains paused regardless of wall-clock time. Canceling logout changes nothing. No closed-browser notification is promised. [Covers PRD AC-4 and Resolution 1]
13. **AC-013 — Plant growth:** At elapsed percentages below 25%, from 25% to below 60%, from 60% to below completion, and after persisted completion, the UI shows Seed, Sprout, Small plant, and Full plant respectively in text and art. Reduced-motion mode performs static changes. [Covers PRD AC-5]
14. **AC-014 — Idempotent completion:** Completing one linked focus creates exactly one final completed session, one mature Garden plant, one task increment, one in-app alert, and at most one sound/notification. Replaying completion, refreshing, and concurrent tab synchronization create no duplicates. The Full plant is not shown as saved before persistence succeeds. [Covers PRD AC-6]
15. **AC-015 — Give up:** Give up from active and paused states opens a dialog focused on Keep focusing. Cancel/Escape leaves time and state unchanged. Confirm creates exactly one Ended/Withered History result, no completed Garden plant or task credit, and later completion attempts fail. [Covers PRD AC-7]
16. **AC-016 — Break flow:** The fourth default completed focus offers a long break; preceding completions offer short breaks. No break starts before Start break. A completed or skipped break grants no plant/task credit. Skipping the long-break offer resets the interval, and the next completed focus offers a short break. [Covers PRD AC-8]
17. **AC-017 — Garden:** Garden displays only the signed-in user’s completed plants with type/date/planned duration, while History displays withered results separately. Empty, loading, error, retry, and stale/offline states match the UX plan. [Covers PRD AC-9]
18. **AC-018 — Feedback and notifications:** Completing one focus and one break yields one in-app alert each without requesting permission. Sound on/off is independent. Permission appears only after Enable Notifications. Granted permission permits one generic notification; denied, revoked, and unsupported states show the fallback and never block or repeatedly prompt. [Covers PRD AC-19/AC-20]
19. **AC-019 — Failure honesty:** Simulated task/settings/session/Garden write failures retain recoverable input/state, show a specific retry or reauthentication action, and do not display the failed change as saved. A plant-art failure leaves all timer controls and textual stage information usable.

### Security checks

20. **AC-020 — Ownership matrix:** With User A and User B, User A cannot list, fetch, select, change, delete, pause/resume/give up/complete, or otherwise infer User B’s settings, tasks, timers, sessions, Garden, History, or account data by replacing any identifier in path, query, headers, or body. Both existent and nonexistent unauthorized identifiers produce non-disclosing responses. [Covers PRD AC-12]
21. **AC-021 — Password storage and secrets:** Database inspection shows adaptive salted password hashes and non-recoverable reset credentials, never plaintext. Repository and built-client inspection find no private secret. Logs from registration, login, reset, task, and timer failures contain no password, token, reset credential, sensitive task title, query detail, or user-facing stack trace. [Covers PRD AC-23/AC-27]
22. **AC-022 — Validation and XSS:** Boundary tests reject wrong types, malformed identifiers, over-limit strings, forbidden state transitions, and invalid ranges. Representative `<script>`, event-handler, URL, and markup payloads in task titles render as inert text and execute no script in lists, selectors, results, History, or errors. [Covers PRD AC-25]
23. **AC-023 — CSRF and CORS:** A state-changing request without a valid CSRF proof, with another session’s proof, or from an unapproved origin changes no data. Preflight and credential checks permit only documented frontend origins and required methods/headers; no wildcard credentialed origin is returned. [Covers PRD AC-25]
24. **AC-024 — Abuse controls:** Exceeding each documented registration/login/reset threshold yields a generic `429` for the rest of its window without confirming account existence. Requests below the threshold remain usable, and local development does not silently disable the controls. [Covers PRD AC-26]
25. **AC-025 — Headers and transport:** Deployed HTTP requests redirect to HTTPS; authenticated pages contain no active mixed content. Header inspection confirms the documented CSP, `frame-ancestors`, MIME sniffing, referrer, and permissions policies without breaking P0 flows. [Covers PRD AC-26]
26. **AC-026 — Dependency and threat review:** Before release, documented threat-model coverage exists for every NFR-011 threat. The dependency/security scan has zero unresolved critical findings, and every high finding has either a fix or a named owner, mitigation, and approval. [Covers PRD AC-27]

### Accessibility checks

27. **AC-027 — Keyboard operation:** A keyboard-only user can register, log in, reset a password, create/edit/complete/reopen/delete a task, configure settings, start/pause/resume/give up/complete focus, start/complete a break, use Garden filters, control notifications, and log out. Focus is always visible and follows the dialog/save/delete/result rules. [Covers PRD AC-10]
28. **AC-028 — Semantics and announcements:** Browser accessibility inspection and a screen-reader pass find labeled inputs, associated errors, meaningful headings/landmarks, button names, dialog names/descriptions, textual timer/stage/status equivalents, and restrained live announcements. The countdown is not announced every second; completion and critical errors are announced. [Covers PRD AC-10]
29. **AC-029 — Non-sensory equivalence:** With color distinction unavailable, sound off/failing, notifications denied/unsupported, images unavailable, and reduced motion enabled, every timer state, task state, outcome, validation error, permission state, and next action remains understandable and operable. [Covers PRD AC-10/AC-19/AC-20]
30. **AC-030 — Contrast:** Automated and manual checks of final default, hover, focus, active, selected, disabled, error, and dialog-overlay states confirm at least 4.5:1 normal-text contrast and 3:1 large-text, meaningful non-text, and focus-indicator contrast. Known failing palette pairs listed in UX plan §7.2 do not carry meaning alone.

### Responsive and compatibility checks

31. **AC-031 — Representative viewports:** The complete public/auth, Focus, Tasks, Garden, and Settings flow passes at 320×568, 375×667, and 390×844 CSS px portrait and 844×390 landscape, with no horizontal page scroll, clipped content, hidden action, or hover-only control. [Covers PRD AC-21]
32. **AC-032 — Touch, safe areas, and keyboard:** At every AC-031 viewport, measured P0 controls are at least 44×44 CSS px. Representative top/bottom safe-area insets do not cover controls. With a mobile keyboard open, the focused field, error, Save/submit action, and navigation remain reachable. [Covers PRD AC-22]
33. **AC-033 — Zoom reflow:** At 200% browser zoom, each P0 screen reflows to one readable column where needed; controls and long 200-character task titles wrap without clipping or two-dimensional scrolling, and browser/pinch zoom remains enabled. [Covers PRD AC-22]
34. **AC-034 — Browsers:** P0 flows pass on current stable Chrome, Edge, Firefox, and available Safari. Any unavailable Safari test is recorded as a release constraint. Notification unsupported mode passes independently through in-app fallback. [Covers PRD AC-13]
35. **AC-035 — Performance:** Core-screen usability occurs within 3 seconds on the documented device, browser, connection, build mode, and cache state. The result records the actual profile rather than claiming an unspecified benchmark. [Covers PRD NFR-1]

### Release completeness

36. **AC-036 — Documentation:** A reviewer can identify architecture, prerequisites, configuration, migration order, scripts, local email behavior, local-versus-production security behavior, HTTPS deployment, and exact start instructions solely from root `README.md` and the two `.env.example` files.
37. **AC-037 — Build quality:** Documented install, type-check, lint, production build, migration, and dependency/security commands complete successfully. Invalid required environment configuration fails with a clear sanitized error.
38. **AC-038 — Scope integrity:** Navigation and code expose no placeholder Stats, categories, rewards/coins/shop, social, admin, dark mode, ambient audio, guest mode, native-app behavior, or push delivery. No fake API record, auth bypass, embedded credential, unlicensed asset, automated test file, or nonfunctional button is present.

## Out of Scope

- P1 task categories, category totals, statistics, streaks, charts, coins, rewards, shop/catalog locking, purchases, and unlock rules.
- P2 display name/avatar editing, guest mode, achievements, rare plants, ambient sound, dark mode, friends, leaderboards, group focus rooms, admin tools, onboarding, weekly summaries, and streak freeze.
- Task descriptions, due dates, search, subtasks, dependencies, recurring tasks, file attachments, calendar integration, sharing, collaboration, and team/company workspaces.
- Native iOS/Android applications, native-app claims, full offline-first support, service workers/PWA push, backend push infrastructure, or any promise of notification delivery while the browser is fully closed.
- Website/app blocking, strict-focus tab monitoring, tab-history collection, attention surveillance, invasive device monitoring, or claims that Rootine proves continuous focus.
- Payments, subscriptions, real-money purchases, advertising, undisclosed analytics, medical claims, and guaranteed productivity outcomes.
- Account export/deletion UI and a final public-retention policy until PRD OQ-10 is resolved.
- Pause/Resume/early-end controls for active breaks, automated break start, and any abandonment penalty not stated in Resolution 1.
- More than the three complete P0 plant types or externally licensed visual/audio assets.
- Automated unit, integration, or end-to-end test files. Acceptance remains mandatory through documented manual checks, API inspection, build/lint/type checks, browser tools, and security/dependency scans.
