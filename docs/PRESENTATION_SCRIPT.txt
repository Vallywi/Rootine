3:45 - 4:35   JERICKO: ARCHITECTURE AND TECHNOLOGIES
==========================================================================
[SLIDE 16: How it is built (divider), then SLIDE 17: Architecture diagram. Then SLIDE 18: Technology stack, when talking about React, Express and the database. Then SLIDE 19: Security and secrets, for the .env and .gitignore part.]

JERICKO:
Thank you, Jecyn. Rootine has three layers.

The frontend is React 19 with Vite, and a PWA plugin that makes it installable. Each screen is one file in
frontend/src/pages.

The backend is Node.js with Express 5. Each feature has its own router: auth, tasks, sessions, garden, shop,
friends, and chat. Every request is validated with a library called zod. We also use helmet for security
headers, a CSRF header on every write, rate limits, and hashed passwords.

The database is PostgreSQL. In production it is Supabase, and the app is hosted on Vercel. For local use and
tests, we use PGlite, which is real PostgreSQL running inside Node, so nobody needs to install a database.

Secrets like the database URL and the AI key stay in a .env file that is in .gitignore. The repository only has
a .env.example with empty placeholders.

4:35 - 5:45   JERICKO: THE EXTERNAL API - GOOGLE GEMINI
==========================================================================
[SLIDE 20: Our external API, Google Gemini. Then switch to the live app and open the chat drawer.]

JERICKO:
Our external API is Google Gemini. It powers Rootie, the chat assistant.

We chose Gemini because it has a free tier, it uses plain JSON over HTTPS so we did not need extra libraries,
and it writes short, natural answers.

[LIVE APP: type "How is my progress this week?" and send. Read the reply aloud. If the API is busy, show that error message instead.]

Here is what happens when I send this question. The browser calls our own server at /api/chat. The server checks
that I am logged in, applies a limit of 30 questions per hour, and validates the input: at most 10 messages and
500 characters each.

Then the server builds a snapshot of my own data from the database: focus minutes, streaks, plants, tasks, and
badges. The browser cannot add facts to it. Other users' data, emails, and friends' progress are never included.
The server sends that snapshot and the question to this endpoint:

  POST https://generativelanguage.googleapis.com/v1beta/models/{model}:generateContent

[SLIDE 21: What happens when you ask Rootie (six steps). Optional: show backend/src/ai.js in VS Code.]
The API key travels in a request header, never in the URL, and it only exists on the server. Gemini replies with
JSON, and we read the text from candidates, content, parts.

For errors: the request times out after 15 seconds. If Gemini is busy with a 503, we retry once. If it is rate
limited with a 429, the user sees "The assistant is busy right now." Other failures show "not available" without
provider details, so the key cannot leak. An empty answer has its own message. And without a key, the rest of
the app still works.

5:45 - 6:30   AILISH: DESIGN PATTERN - STRATEGY
==========================================================================
[SLIDE 23: Design pattern, Strategy (diagram). Then SLIDE 24: The pattern in our real code. Optional: open backend/src/db.js in VS Code.]

AILISH:
Thank you, Jericko. Our design pattern is Strategy, which means several interchangeable implementations behind
one interface.

In db.js, a function called createDb checks the configuration. With a DATABASE_URL it returns the Supabase
PostgreSQL driver. Without one, it returns the local PGlite driver. Both have the same methods: query, tx for
transactions, migrate, and close.

So every route just calls ctx.db.query and never knows which database it uses. That solves a real problem. The
same code runs in production, on a grader's laptop with nothing installed, and in tests with a fresh in-memory
database each time.

Why not the alternatives? An if-production check in every route would repeat logic in about ten files. A
Singleton gives one shared instance that cannot be swapped, so tests would share state. And a mocked database
would not run real SQL.

The AI client follows the same idea: the chat route only needs one method, reply, so our tests plug in a fake AI.

POSSIBLE QUESTIONS - WHO ANSWERS AND SHORT ANSWERS
==========================================================================
Q: Why does the server handle the timer?                                     (Jecyn)
A: So users cannot cheat by changing the browser clock, and the timer survives refreshes.

Q: Where is the API key kept?                                                (Jericko)
A: In backend/.env locally and in Vercel environment variables in production. Never in the repository.

Q: What if Gemini is down?                                                   (Jericko)
A: The user gets a clear message, and the rest of the app keeps working.

Q: How do you stop the AI from leaking other users' data?                    (Jericko)
A: The server builds the snapshot from the logged-in user's own rows only. A test checks that another user's
   name and any email are not in the prompt.

Q: What is prompt injection, and what did you do about it?                   (Jericko)
A: A user could write a task title that looks like an instruction. The system prompt says the data and task
   titles are untrusted text and must never be followed as instructions.

Q: What does Strategy give you over an if statement?                         (Ailish)
A: One place chooses the driver, routes stay unchanged, and tests can use a fresh in-memory database.
